# Code quality metrics: local tools with a generated page

## Context and Problem Statement

The statement asks for quality metrics of the source code and refuses documentation outside the repository (PROYECTO_FINAL.pdf, p. 9).

## Decision Drivers

- Everything the evaluator needs is inside the repository.
- Metrics are regenerated by CI.

## Considered Options

- SonarCloud
- Local tools (linter, coverage, complexity, duplication) with a generated page

## Decision Outcome

Chosen option: "Local tools (linter, coverage, complexity, duplication) with a generated page", because the metrics are then versioned and delivered with the archive.

### Consequences

- Good, because the quality page is regenerated at each merge to main (step F3).
- Bad, because no hosted history of the metrics.

### Confirmation

The generated page shows coverage, lint findings, complexity and duplication, and its date matches the last commit of main (step F3). Linter and coverage are already configured in `pyproject.toml`. This record is accepted when the pull request that adds it is approved by the decision-makers.

## Pros and Cons of the Options

### SonarCloud

- Good, because: Recognized dashboard, free for public repositories.
- Bad, because: Results live outside the repository.

### Local tools (linter, coverage, complexity, duplication) with a generated page

- Good, because: Everything stays in the repository.
- Bad, because: Less polished.
